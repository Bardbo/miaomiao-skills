# 公司调研协议

## 首要原则

**公司调研的价值不在"了解这家公司"，而在校准排序与语气。**

优先级：

1. **这家公司真正在招什么人**（最高价值 → 影响条目选择）
2. **这家公司用什么语言说话**（影响技术栈关键词的呈现方式）
3. 公司历史与文化（基本没用，不要浪费时间）

调研结论若不能转化为"选哪条经历"或"用什么词"，就是无效调研。

---

## 调研白名单

| 可查 | 用途 |
|---|---|
| 官网在招的同岗位 JD | 校准要求，最高价值 |
| **同类公司同岗位 JD（5-10 家）** | 横向对比，见 `jd-analysis.md` |
| 技术博客、开源仓库 | 技术栈与工程偏好 |
| 公开财报、融资公告 | 业务方向与阶段 |
| 公开的组织结构、团队名 | 团队规模推断 |

## 调研黑名单

| 不可用 | 原因 |
|---|---|
| 员工匿名吐槽（脉脉、Blind 等） | 主观、无法验证、偏见重 |
| 薪资推测 | 无法验证，且不影响简历内容 |
| "据说"的文化与氛围 | 无法给出 URL |
| **任何无法给出 URL 的断言** | 一律不采用 |

**没有 URL 就没有事实。** 这一条能挡掉 90% 的幻觉。

---

## 置信度分级（红线）

| 置信度 | 定义 | 允许用途 |
|---|---|---|
| **high** | 有可访问 URL 的公开事实 | **可写入简历正文** |
| **mid** | 合理推断（业务方向、技术栈、团队规模） | **只影响排序与取舍** |
| **low** | 主观判断（文化、氛围、偏好） | **只影响语气与篇幅** |

### 红线：mid / low 绝不进简历正文

理由很实际——**写进去之后，用户面试时根本不知道自己"说过"这些，一问就崩。**

举例：AI 调研推断"该公司技术氛围偏极客"，于是简历里写了"追求极致性能"。面试官问"能举个你极致优化的例子吗"，用户答不上来，因为他从来没在意过这件事。

### 数据结构

```yaml
company_brief:
  fetched_at: 2026-08-29T11:05
  facts:                          # high，可进正文
    - claim: 增长中台使用 Flink + ClickHouse
      source_url: https://...
      confidence: high
  inferences:                     # mid/low，只影响排序与语气
    - claim: 团队规模约 30 人
      confidence: mid
      used_for: ordering
    - claim: 技术氛围偏极客
      confidence: low
      used_for: tone
  failed_queries: ["未找到公开的团队组织结构"]
```

**`used_for` 字段是硬约束**：每条 `inferences` 必须声明用途，且只能是 `ordering`（排序）或 `tone`（语气）。写不出用途的推断 = 无效，删掉。

---

## 幻觉风险：本环节是全链最高

LLM 会一本正经地编出"该公司 2025 年完成 C 轮融资，专注 XX 领域"。**语气越确定，越危险。**

### 强制要求

1. 每条 `facts` 必须带 `source_url` 与 `fetched_at`
2. 抓取失败或查不到 → 写入 `failed_queries`，**不编**
3. 输出时若 `facts` 为空，明确告知用户："未获得可验证信息，本版未针对公司做额外调整"

**沉默比幻觉好。**

---

## 缓存复用

```yaml
# 同一公司 30 天内复用 company_brief.yaml
# 跨岗位共享（同公司投多个岗位时，只重跑 JD 解析）
```

缓存目录：`targets/<公司>/company_brief.yaml`，跨岗位共享。

超过 30 天或用户提供了新信息 → 重新调研。

---

## 优先级建议（时间有限时）

如果调研时间有限，按此顺序分配：

1. **同类岗位 JD 横向对比**（收益最高，零幻觉风险）
2. 目标公司官网在招的同岗位 JD
3. 技术博客 / 开源仓库
4. 其他

第 1 项做完了，即使后面全跳过，定制质量也有保障。

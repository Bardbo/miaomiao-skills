# 回流提案机制

## 定位

**AI 判断，用户裁决。**

定制过程中会产生一些好表述、新事实。这些东西应该回到母版，让下次定制受益。但自动回流会污染母版，所以必须过用户这道关。

---

## 三类分流

| 类型 | 说明 | AI 默认建议 | 可否自动 |
|---|---|---|---|
| **A 事实新增 / 修正** | 用户口述补充的新事实（新数字、新项目、新时间） | 回流 | 可（低风险） |
| **B 表述优化** | 同一事实的更好说法 | 回流，但**不覆盖 `raw_input`** | 需确认 |
| **C 推断填充** | AI 为贴合 JD 补的内容 | **禁止回流** | ❌ 硬闸门 |

### C 类闸门必须焊死

**理由**：不是不信任用户，而是用户到第 5 次裁决时，已经记不清哪些是自己说的、哪些是 AI 编的。

一旦推断内容进了母版，它就变成了"用户提供的原始材料"，下次定制时会被当作事实引用。**污染是不可逆的。**

判定为 C 类的特征：
- 母版中完全没有对应信息，AI 根据 JD 反推补上的
- 数字是"合理估计"而非用户所说
- 技能是从经历中"推断"出来的（用了 Flink → 推断会 Kafka）

---

## 提案格式

**每条提案必须包含 AI 的判定理由。** 只给结论不给理由的提案，等于让用户盲签。

```markdown
### 提案 3 / 共 5

- **类型**：B 表述优化
- **位置**：exp-007-a1
- **原文**：参与了用户增长归因链路的重构
- **建议**：负责增长归因链路的 Flink 实时化改造，将归因延迟从 24 小时降至 5 分钟
- **AI 判定理由**：该岗位 P1 含「Flink / 实时计算」，原表述未体现技术栈，JD 命中率低。
  新表述所有事实均来自 exp-007-a1，未引入新信息，证据状态仍为 pending。
- **风险**：低。但"负责"隐含主导性，若团队 4 人中你只做算子部分，面试可能被追问。
- [ ] 采纳　[ ] 拒绝　[ ] 采纳但改为「参与」
```

### 三个必答问题

AI 在生成提案时必须回答，并写进判定理由：

1. **这条改动引入了新事实吗？**（是 → C 类，禁止回流）
2. **原文 `raw_input` 会被覆盖吗？**（会 → 违规，只能写进 `rewrite_candidates`）
3. **如果被面试官追问，用户答得上来吗？**

---

## 用户裁决

三种动作：

| 动作 | 效果 |
|---|---|
| **采纳** | 写入母版 |
| **拒绝** | 丢弃，不重复提议同一条 |
| **采纳但修改** | 用户给出新措辞，按用户的写 |

**AI 只给建议，不自动执行。** 哪怕判定为 A 类低风险，也要走一遍确认——除非用户明确授权"以后 A 类自动回流"。

---

## 母版升版流程

用户裁决完成后：

```
1. accepted 提案批量写入母版
2. master.version += 1
3. 写 changelog（变更内容 + 来源提案）
4. 扫描所有 tailored.yaml，找出 master_version < 当前版本 的
5. 标记这些定制版：「母版已更新，建议重新生成」
6. 生成 Markdown 预览
```

第 4-5 步很重要：**母版变了，之前生成的定制版就过期了**。不提醒用户，他会拿着旧版去投。

## rewrite_candidates 机制

B 类表述优化**不覆盖 `raw_input`**，而是追加到数组：

```yaml
achievements:
  - id: exp-007-a1
    raw_input: 参与了归因链路重构          # 永不改动
    action: 重构
    ...
    rewrite_candidates:
      - text: 负责增长归因链路的 Flink 实时化改造
        from_target: 字节跳动-后端
        adopted: false
```

好处：
- 随时能回溯用户原话
- 同一事实的不同说法都保留，下次定制可复用
- 定制时优先从 `rewrite_candidates` 里挑，减少 LLM 自由发挥

---

## 拒绝重复提议

用户对某条提案点"拒绝"后，记录到 `dismissed_proposals`，后续定制不再提议同一条。

反复提议被拒的内容，是最让人烦躁的交互。

# 改写规则

## 核心立场：选择优于创作

定制不是"为这个岗位写一份新简历"，而是"从母版里挑出最合适的部分重新组织"。

**定制版不存内容副本**，只存 `master_version` + 条目 ID 列表 + 改写策略。好处：
- 母版升级时能算出哪些定制版受影响
- 内容只有一个真源，不会多份定制版各说各话
- 无法绕过母版凭空生成内容

---

## 四层模型

| 层 | 操作 | 风险 | 默认 |
|---|---|---|---|
| **L1 排序** | 调整经历与 bullet 的先后顺序 | 无 | 开 |
| **L2 裁剪** | 决定哪些条目出现或隐藏 | 无（信息变少，不外溢） | 开 |
| **L3 侧重** | 同一事实换个说法、换个重点 | 低（需防漂移） | 开 |
| **L4 新增** | 写母版里没有的内容 | **高** | **硬 Gate 拦截** |

L1-L3 的共同点：**都在母版池内操作，不产生新事实**。

### L4 的处理方式

L4 不该被"禁止"——那会让 LLM 卡死。正确的处理是**拦截后转成明确动作**：

> 触发 L4 时，不要写进定制版。而是：
> 1. 在母版中新建一个条目，标记 `evidence: pending`
> 2. 写入 `gaps`，告诉用户"这个岗位需要 X，你的母版里没有，建议补充"
> 3. 定制版中**不体现**这条内容

这样既保证了真实性，又让用户知道缺什么。

### ⚠ pending 有两种，不能用一把尺子量

`pending` 的默认待遇是「不进成稿」。这条规则单独看是对的，但它把两类性质完全不同的
东西混为一谈 —— **误伤的往往是简历里最硬的内容**。

| | **① 存疑**（事情本身不确定） | **② 未采集**（事情确定，细节没填） |
|---|---|---|
| 例子 | 「训练过 LoRA」但没成品；「主导了项目」但说不清自己做了什么 | 专利已授权，只缺专利号；论文已录用，只缺作者位次 |
| 问句 | **这事到底成没成？** | **这事的编号/位次/日期是多少？** |
| 待遇 | **隐藏**。补的是"事实本身" | **放行**。补的只是"可查证编号" |
| 转出条件 | 拿到证据 → `self_reported` | 本人确认 → `self_reported`（细节后补） |

**判据：把缺失的字段删掉，剩下的句子还成立吗？**

- 「一种公交线路优化调整方法及装置　—　发明专利，已授权」→ 成立 → 属②，放行
- 「图像生成模型定制：自建数据集训练 LoRA」→ 成立，但"有没有训出能用的东西"不确定 → 属①，藏

**②类的正确写法 —— 骨架表述：**

```yaml
evidence: self_reported      # 不是 pending：事实存在，细节待补
needs_confirm: true
confirm_what: [专利号, 授权日期, 发明人位次, 权利人]
```

渲染时用 `clean_val()` 滤掉「待确认 / 待补」开头的**字段值**，成稿只留成立的那部分。
**（题目待补）这类 title 占位符不滤** —— 它是给草稿看的待办，滤掉等于连提醒一起删了。

**为什么必须放行而不是等补齐：** 一份连成果段都没有的社招简历，说服力全靠自述。
藏掉已授权专利的代价（"这人没什么可查证的"），远大于"位次答不上来"的代价。
**但放行的代价要写进 `evidence_note`，并让用户确认** —— 面试必问编号和位次，
这是从加分项变成风险点的分界线。

## 两个独立维度：profile 写什么，polish 怎么写

改写前必须先定这两个参数。它们**正交**，且都**不能解锁 evidence 限制**。

| 维度 | 管什么 | 取值 | 存在哪 |
|---|---|---|---|
| **`profile`** | 结构与取舍——写什么、不写什么、谁在前 | `campus` / `junior` / `experienced` / `expert` | 母版 `preferences.profile` |
| **`polish`** | 表达强度——同一事实说到几成 | `sincere` / `balanced` / `bold` | 母版 `preferences.polish` |

**它们的分工一句话**：profile 决定保留哪些素材，polish 决定保留下来的素材说到什么程度。
profile 是**筛选器**，polish 是**放大器**。放大器不能放大没被选中的东西。

## profile：人群与阶段画像

**先判断，再动手。** 不同画像的简历几乎不是同一种文体——把社招简历写成校招格式，和把校招简历硬撑成社招格式，都是灾难。

| profile | 判断依据 | 教育段位置 | 校园内容 | 技能段 | 篇幅 |
|---|---|---|---|---|---|
| `campus` 校招 | 应届、实习、毕业 <1 年 | **置顶** | 保留：学生工作 / 竞赛 / 核心课程 / GPA | 可全列，**无佐证也允许**（无深度是常态，不是缺陷） | 1 页 |
| `junior` 初级 | 1–3 年 | 次位（经历之后） | **降级**：只留高含金量竞赛与奖学金，删学生工作 | 收敛到有佐证 + 与目标相关 | 1 页 |
| `experienced` 社招 | 3 年+（**默认**） | **沉底** | **全部删除** | 只留有佐证或强相关，**≤10 项** | 1–2 页 |
| `expert` 资深 | 8 年+，或有代表作 | 沉底，一行带过 | 全部删除 | **不列技能清单**，能力写进经历 | 2 页内 |

### 校园内容的判定

凡是 `student_era: true` 的条目（学生工作、三好学生、校园竞赛、课程成绩），在 `experienced` / `expert` 下**一律不出现**。

这不是因为它假，而是因为**它会稀释信号**。社招 HR 只关心"你能在我的岗位上立刻产出什么"，一条"曾任学生会部长"占掉的那行空间，本可以放一句能证明你能干活的话。

**校招反过来**：这时候没有工作经历，校园内容就是主战场，全删等于自废武功。

### 技能段的收敛（社招最容易犯的错）

技能堆叠是社招简历的**负分项**，不是加分项。21 项技能里 13 项找不到任何项目佐证，HR 的读法不是"这人懂得多"，而是"什么都沾一点，什么都不深"。

社招技能段的硬指标：

1. **≤ 10 项**。`experienced` 下超出即触发告警。
2. **每一项都要能在某条 bullet 里找到对应**。找不到的（evidence_refs 为空）默认隐藏，除非显式 `keep: true`。
3. **过时技术归档而非删除**。母版是"什么都有"的超集，删了就没了。用 `status: archived` 标记——默认不显示，换方向时可手动开启。

> 例：投 AI 岗时 TransCAD / SUMO / SVM 归档；改投交通规划岗时它们复活，LangChain / RAG 归档。
> **同一个人，不同方向，技能段应该是不同的。**

4. **技能是翻译层，不是炫耀层**。只写"能立刻上手干活"的，不写"学过"。

### 篇幅与摘要

| profile | 摘要段 | 说明 |
|---|---|---|
| campus | 可有 | 一行定位即可 |
| junior | 不必 | 经历还不够撑摘要 |
| experienced | 建议有 | 3 行内：我是谁 / 最强的一段 / 为什么匹配 |
| expert | 必须有 | 定位句 + 代表作规模数字 |

## 技能表达范式：从工具清单到能力证据

> **收敛管的是"列几项"，范式管的是"该不该列"。** 范式是更上游的问题——
> 一个能力若已商品化，就算只有 3 项技能，列它也是浪费版面。

### 核心判断：装个工具就能获得的能力，写在简历上没有区分度

2026 年的具体情形，都是真的能力，但都已经是**行业基线**：

- **SQL** —— 用的时候让 AI 写，语法本身不再是技能
- **RAG / Agent** —— 框架开箱即用，调一次 API 就能跑通
- **大部分"熟悉 X 框架"** —— 装上就能用

基线能力单列，等于在简历上写"熟练使用搜索引擎"。**不是假话，但没有信息量**。
它会挤占版面，还会让 HR 把整段技能读成"这人在凑数"。

### 技能的三层价值

| 层 | 定义 | 判断问句 | 处理 |
|---|---|---|---|
| `commodity` 基线 | 工具化，人人可得 | **装个工具、问一句 AI 就能获得吗？** | **不单列**。藏进交付物里当注脚 |
| `capability` 交付 | 能独立从 0 到 1，并交付给别人用 | **它对应某个具体的、别人真的在用的东西吗？** | **主战场**。必须挂交付物 |
| `leverage` 杠杆 | 放大产出效率的能力 | **它让你一个人干出几个人的产出吗？** | **单列**。2026 年的稀缺品 |

`kind` 字段写进母版，渲染器按层处理，`commodity` 默认不单列——
**规则进脚本才不会被绕过**，靠提示词约束会在第 N 次改写时被忘掉。

### 反直觉推论：AI 时代，"离开 AI 也能做"从减分项变成加分项

这是本节最重要的一条，也是多数人还没转过弯的地方。

当所有人都在用 Copilot / Claude Code 时，**"会用 AI 工具"已经没有区分度了**——它正在变成 `commodity`。
真正稀缺的反而是两个方向：

1. **在无 AI 的隔离环境里独立交付**（内网、涉密、无外网、无云）
   → 证明能力是**内化的**，不是外包给工具的。把 AI 拿走，你还在不在？
2. **把 AI 纳入真实工作流并产出交付物**（而不是只会聊天问问题）
   → 证明能把杠杆**变成产出**，而不只是消费别人的产出。

共同点：**可验证**。前者有交付物，后者有工作流。

> 例：同一个人，同样会 Python + SQL
> - 老土写法：`熟悉 Python、了解 SQL` —— 两条基线技能，零区分度
> - 新写法：`在内网隔离环境下独立搭建数据分析平台（Flask + Streamlit + MySQL），
>   交付后由业务同事直接使用`
>
> 事实一点没变，但后者同时证明了：需求理解、架构选型、全栈交付、落地推广。
> SQL 藏在里面，不需要单列——**它从"我会什么"降级成了"我用什么做的"**。

### 写法转换表

| 老土写法 | 新写法 | 为什么 |
|---|---|---|
| 熟悉 SQL | （删）挂进交付物 | AI 能写，零区分度 |
| 熟悉 LangChain | （删）改说用 AI 工具链交付了什么 | 开箱即用；写了却拿不出东西 = 负分 |
| 熟悉 RAG / Agent | 除��从零实现过检索/编排链路，否则不写 | 同上 |
| 熟悉 Python | 挂到交付物 | 语言不是卖点，用它做出来的东西才是 |
| 会用 AI 写代码 | 以 AI 辅助开发为主要工作方式，独立完成 X | 工具人人可装，工作流才是你的 |
| 了解 Docker / Linux | （删）或挂进部署交付 | 基线 |

### 商品化能力的两个例外（必须写的情况）

1. **JD 明确点名时** —— 关键词匹配是机器筛的，不写连初筛都过不了。
   此时写进 `tech_tags` 或交付物的括号里，**不占独立条目**。
2. **受限/合规环境要求的** —— 如内网工具链，写出来说明你懂边界。

### AI 原生能力（`leverage`）怎么写

**不写工具清单**——工具名人人可装，列出来又是另一种凑数。
写**工作流与自建体系**：

- 工具名可以出现，但作为**附注**，主句必须是能力
- 自建的记忆 / 上下文体系是强信号 —— 配置它需要动手，不是点一下安装

> AI 原生工作方式：以 AI 辅助开发（vibe coding）为主要工作模式，
> 自建记忆与上下文体系（memos / gbrain），主力工具 Claude Code / WorkBuddy / Hermes

### 与 evidence 的关系

范式管**值不值得写**，evidence 管**能不能写**。顺序是先范式后 evidence：

1. 这条是 `commodity` 吗？→ 是，不单列（**连 evidence 都不用查**）
2. 不是 → 才进入 evidence 流程

**范式也不能解锁 evidence。** 一条 `commodity` 且 `pending` 的内容，两头都不该出现。

## 「low 感」禁用清单

> 本节回应一句最常见的评价：**「整体简历显得很 low」**。
>
> low 不等于「写得不好」，也不等于「内容不行」。它的准确含义是：
> **读起来像一个不会写简历的人写的** —— 事实可能全是真的，但每一处细节都在告诉对方
> 「我没有更硬的东西可放了」。
>
> 这一节里的每条都**已经落进渲染器或校验器**。靠提示词约束会在第 N 次改写时被忘掉。

### 判定口诀

> **这一条，是让对方更想面试我，还是让对方看出我没东西可写？**

答不上来就是后者，删。

### 清单

| # | low 写法 | 为什么 low | 落地点 |
|---|---|---|---|
| 1 | 技能后跟「（熟悉）」「（精通）」 | 自评不可查证。写「精通」是邀请对方追问到崩；「熟悉」在 HR 默认读法里 ≈ 不精 —— **越描越黑** | 渲染器 `SHOW_SKILL_LEVEL = False`。`level` 保留在母版，仅供内部收敛决策 |
| 2 | 荣誉段只剩「优秀团员」「积极参与」 | 无竞争性荣誉上简历不是加分，是告诉对方「我把能找到的都写上了」 | 渲染器 `HONOR_MIN_RELEVANCE` 门控：**没有硬通货就整段不出现**（`force: true` 可显式开启） |
| 3 | 技能按「编程语言 / AI 框架 / 人工智能 / 工具与环境」分类 | 这是**零件清单**，且「AI 框架」与「人工智能」互相打架。分类混乱 = 本人没想清楚自己会什么 | 渲染器 `CATEGORY_ORDER`：按**能力域**（做什么）而非**技术类型**（是什么） |
| 4 | 单列工具名 | 同 `commodity` 陷阱 | 范式层已覆盖；v10 起另加 `stack` 字段强制工具名降级为注脚 |
| 5 | 一行只有一个词的分组（如「工程与交付：Python」） | 空组/独组是凑数的直接证据 | 同组至少 2 项，或写成能力陈述（如「内网隔离环境下的全栈交付（Flask / Streamlit / MySQL）」） |
| 6 | 证书段只剩 CET-4/6、计算机等级 | 对硕士学历者，CET-6 已被学历覆盖，单列反而暴露没东西写 | 校验器 draft 提示（不拦截 —— 证书是可查证事实，性质与荣誉不同） |
| 7 | 方法段用「、」平铺罗列六七个动作 | 读起来是流水账，不是能力陈述 | 改为「→」串联（数据集构建 → BERT 微调 → 部署上线 → 监测维护）。**只压缩，不新增** |
| 8 | 同一所学校拆成两块（本硕各一块） | 版面碎，且读不出「7 年在同一所学校」这个稳定信号 | 渲染器自动合并，学位各占一行 |
| 9 | 把 AI 能力单独开一个段 | 等于宣告「我的 AI 能力和专业能力是两回事」，还多出一个只有三行的碎段落 | v10：`ai_native` 按 `group` 并入「专业技能」 |
| 10 | 简历里出现「待确认」「待补」 | 占位符出现在成稿 = 敷衍 | 渲染器 `pending` 在 final 模式隐藏；摘要里的占位符是 ERROR |
| 11 | 「熟练掌握 Office」「抗压能力强」「具有良好的团队精神」 | 零信息量，且是模板腔 | 不写。需要时改用事实呈现 |
| 12 | 求职意向 | 占首屏，且暗示「海投 / 没想好」 | `show_intention: false`（已有规则） |

### 「stack」字段：工具名降级为注脚

这是范式铁律的推广版 —— **主句必须是能力，工具名只配出现在括号里**。

```yaml
- { id: sk-09, name: BERT 微调, category: 算法与建模, stack: "PyTorch / Transformers" }
# 渲染：算法与建模：BERT 微调（PyTorch / Transformers）
# 而不是：AI 框架：PyTorch（熟悉）、Transformers（熟悉）
```

好处：工具关键词**仍在成稿里**（不影响 JD 机器筛），但它从「我会什么」降级成了「我用什么做的」。
按此规则，PyTorch / Transformers 这类框架可以安全归档 —— 不是删掉，是换个位置。

### 硬通货：什么才算荣誉

| 算 | 不算 |
|---|---|
| 竞赛名次（含具体名次与级别） | 优秀团员 / 优秀干事 |
| 政府或行业奖项 | 积极参与 / 表现良好 |
| 奖学金（含级别与比例） | 无竞争的集体荣誉 |
| 专利、论文（另设段落） | 课程成绩、课程项目 |

**没有硬通货时，荣誉段应当整体消失。** 一个不存在的段落，比一段只有「优秀团员」的段落强得多 ——
后者会拉低整份简历的可信度，而不是加分。

### 摘要：社招最强的去 low 手段，但必须本人确认

没有摘要的社招简历，HR 要读完四段经历才能拼出画像 —— 大多数人不会读那么久。
三行摘要能让首屏立刻成立。

**但它被默认关闭（`summary.enabled: false`）**，因为它是全篇唯一会新增**概括性表述**的段落：

- 只能由**已确认事实**组成 —— 校验器会拦截摘要里出现 `pending` 内容
- 不写自我评价形容词 —— 「学习能力强」是另一类 low
- 须本人确认后才 `enabled: true`

## 泛化：每条规则都有隐含前提（v12）

这一节的每一条都是**用第二、第三个样本撞出来的**。写规则时自认为通用，
换个人就崩 —— 因为规则里藏着没说出口的前提。

### ① commodity 范式的前提：候选人有更硬的东西可放

「装个工具就能获得的能力 = 无区分度，不单列」——这句话漏了半句：
**在有更硬的东西可放时**，才不单列。

反例：大专转行者投入门数据分析岗，母版里 SQL / Excel / PowerBI 全是 commodity，
按规则删光后技能段只剩 1 条，而她投的 JD 原文写着「**必须**掌握 SQL 取数」。
**执行结果不是精练，是自废武功。**

落地：删完若少于 `COMMODITY_FLOOR`(3) 条，把**有项目佐证**的商品化能力放回来。
有佐证说明真用过 —— 它已经通过了「你是不是真会」这一关，不该和凑数的一起删。

### ② 「资深不列技能清单」的前提：对方不用关键词筛你

原设定：expert 画像 `skill: none`，能力全部写进经历。听起来高级，
但中文招聘的初筛是 **ATS 关键词 + HR 按条款勾选**。实测一位 15 年架构师的成稿，
在 JD 的 9 个技术名词里只命中 1 个。

而且它与资深人群的工作性质**结构性互斥**：越资深，做的事越难压进一条 bullet。

落地：expert 也列技能，但严格收敛（上限 6 条且必须有佐证）。

### ③ 引擎默认值里不许有从业者的职业身份

`CATEGORY_ORDER` 曾写着「算法与建模 / 工程与交付 / **智能交通与仿真** / …」。
「智能交通与仿真」是**第一个用户的职业身份**，不是通用能力域。
硬编码进引擎后，会计、销售、架构师的分类全部掉到末尾。

落地：默认值只放跨行业通用能力域；行业特定的由母版用
`preferences.category_order` 自己声明。

### ④ 字段类型必须容错

模板写 `links: [{label, url}]`，渲染器当字符串处理 → 成稿抬头印出
`{'label': 'GitHub', 'url': '...'}`；`result` 填成字符串 → 校验器抛 Python traceback。

**换个人填母版，遇到的第一件事就是满屏堆栈。那是劝退，不是报错。**

落地：渲染器对 dict / str 都接住；校验器对类型错误给中文提示，不抛异常。

### ⑤ 成稿零内部状态

「时间待确认」这类标注曾顶在所有人的成稿上 —— 判定它靠 `period_confirmed`
字段，而这个字段**模板里从未定义过**，于是除了手写过它的人全员中招，
且它没加 `noprint`，会被打印出来。

落地：改为「时间真的残缺才提示」且只在草稿出现；出片后自动校验
「母版 / 出片 / 待补 / 待确认」出现次数必须为 0。

> **元规则：一条规则如果没有写「什么情况下它不成立」，它就还没写完。**
> 从一个样本长出来的 skill，必须靠第二、第三个样本去撞 ——
> 否则你分不清哪些是通用规律，哪些只是第一个人的形状。

## polish：包装级别

### 定位

本 skill 的目标是：**在不脱离真实描述的前提下，把简历写得更有竞争力，提高求职成功率。**

"高大上"不能靠编事实。它靠三种**不产生新事实**的合法手段：

| 手段 | 说明 | 例子 |
|---|---|---|
| **翻译** | 把公司内部土话翻成行业通用术语，对接 JD 关键词 | "写了个日报表脚本" → "搭建项目运行数据自动化分析流程" |
| **聚焦** | 从"我做了什么活"改为"我解决了什么问题、带来什么影响" | "负责垃圾询盘识别" → "构建询盘质量分类模型，自动拦截无效询盘" |
| **层级提升** | 从执行层描述提升到方案层 | "用 BERT 微调做分类" → "基于预训练语言模型的文本分类方案选型与落地" |

三种手段都不伪造事实，但能让同一段经历在 HR 眼里显著升值。这就是 polish 的实质。

### 三档定义

| 级别 | 动词 | 上位概括 | 能力命名 | 缺失数字时 | 适用 |
|---|---|---|---|---|---|
| `sincere` 真诚 | 用本人原话，不升级 | 禁止 | 禁止 | 留空 | 学术 / 体制内 / 本人明确要求 |
| **`balanced` 适度包装**（**默认**） | 升到**证据支持的最高级** | 允许一次 | 允许 | 用定性表述替代 | 绝大多数场景 |
| `bold` 酥化 | 主动叙事重构，成果前置 | 允许多次 | 允许 | 允许合理外推（**须标注**） | 竞争激烈 / 转行 |

### "证据支持的最高级"是核心约束

动词升级不是无条件的。**能升到哪一级，取决于证据，不取决于你想要多好看。**

| 本人原话 | sincere | balanced | bold |
|---|---|---|---|
| 参与 | 参与 | 参与 / 承担 | 仅当能说清具体个人贡献，才升"负责" |
| 负责 | 负责 | 负责 / 主导（确为唯一负责人时） | 主导 / 牵头 |
| 做了 | 完成 | 完成 / 交付 | 交付 / 从 0 搭建（**确为从 0 时**） |

反例——`balanced` 下不允许的升级：
- 4 人团队项目，本人负责其中一个模块 → ❌ "主导整个项目"
- 接手了别人搭了一半的系统 → ❌ "从 0 搭建"
- 只在周会上听过进展 → ❌ "深度参与"

### polish 不能解锁 evidence（硬规则）

**包装级别只调表达方式，不产生任何事实。** 三档下的 evidence 待遇完全一致：

| evidence | sincere | balanced | bold |
|---|---|---|---|
| `verified` | 正常 | 正常 | 正常 |
| `self_reported` | 正常 | 正常 | 正常（强主张提示追问） |
| `pending` | 隐藏 | 隐藏 | **隐藏** |
| `inferred` / `unusable` | 拦截 | 拦截 | 拦截 |

`pending` 在 `bold` 下同样隐藏——**强化包装无证据内容 = 编造**，这是绝对红线。

### 配套：polish 越高，G5 越严

包装后的 bullet 必须扛得住追问，且级别越高要求越严：

| polish | G5 追问层数 | 不通过的处理 |
|---|---|---|
| sincere | 3 层 | 降级或删除 |
| balanced | 3 层 | 降级或删除 |
| bold | **5 层** | **回落到 balanced 表述**，不保留 bold 版本 |

> 说得更漂亮 = 被追问得更狠。写不出来就别写那么满。

### 外推必须标注

`bold` 下允许合理外推（如"服务 X 个部门"→"覆盖全单位"），但：
1. 必须在 `rewrite_candidates` 里记录外推了什么
2. 预览时用 `~` 标记外推表述
3. 出片前必须本人确认

不确认就出片 = 未经授权替用户表态。

## 中文写作规范

### 与英文简历规范的差异（重要）

| 项 | 英文惯例 | 中文惯例 |
|---|---|---|
| 证件照 | 不放（规避歧视诉讼） | **普遍放** |
| 年龄 / 婚姻 | 不写 | 通常不写，但国企 / 事业单位可写 |
| 政治面貌 | 不写 | 国企 / 事业单位**需要** |
| 篇幅 | 严格 1 页 | 1-2 页，资深可 3 页 |

**不要照搬英文简历规范。** 中文简历不放证件照反而显得不完整。

### bullet 写法

```
【动作动词】+【对象】+【方法/手段】+【结果/影响】
```

示例：
- ❌ 负责用户增长系统的开发和维护
- ✅ 重构用户增长归因链路，引入 Flink 实时计算替代 T+1 离线任务，将归因延迟从 24 小时降至 5 分钟，覆盖全量 300 万 DAU

### 动词选择

| 场景 | 动词 |
|---|---|
| 从无到有 | 搭建、设计、建立、从 0 构建 |
| 改进既有 | 重构、优化、改造、升级 |
| 解决问题 | 定位、排查、修复、根治 |
| 推动协同 | 推动、协调、主导、拉通 |
| 产生结果 | 提升、降低、缩短、节省 |

**动词要与 `strength` 匹配**：用"主导"必须 `evidence: verified` 且 `strength: strong`。

## 去 AI 味

### 中文 AI 味禁用词

见 `assets/forbidden_terms.txt`。核心词表：

```
赋能  驱动  闭环  抓手  沉淀  打法  组合拳
从 0 到 1  深度参与  全面负责  极大地
显著的  大幅度的  极大地提升了
```

### 句式特征

| AI 味句式 | 改法 |
|---|---|
| "不仅……而且……" 三段式排比 | 拆成事实陈述 |
| "通过 A，实现了 B，从而 C" 长链 | 砍掉中间推理，只留 A 和 C |
| 每段都以"负责"开头 | 换动词 |
| 形容词堆砌（"极大地""显著的"） | 换成数字 |

### 中文特有的一点

英文 AI 味检测规则（破折号、三段式、-ing 结尾）**译过来不管用**。中文的 AI 味是一套特定词汇 + 特定的"总-分-总"腔调，必须自建词表。

本机 `humanizer-zh` 技能的规则译自英文语料，直接用于中文简历效果有限。

| 场景 | 建议 |
|---|---|

## L3 侧重的风险：表述漂移

同一条经历投 10 个公司，会产生 10 种说法。风险在于：

- 说法越来越漂亮，离事实越来越远
- 用户面试时说的和简历上写的对不上

### 防护

1. 每次 L3 改写产生的好表述，写入 `rewrite_candidates[]`（**不覆盖 `raw_input`**）
2. `claim_ledger` 记录每次对强主张的降级或质疑
3. G5 反向面试会兜底：扛不住追问的 bullet 降级或删除

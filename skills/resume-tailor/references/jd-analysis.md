# 岗位解析

## 输入要求

需要用户提供三项：

1. **目标公司**（尽量精确）
2. **岗位名称**（含方向，如"后端工程师（增长方向）"而非"后端"）
3. **JD 原文**（粘贴或给链接）

### 信息不全时

| 缺失 | 处理 |
|---|---|
| 无 JD | 引导用户提供；或标注"未获得 JD，本版按同类岗位通用要求定制" |
| 只有公司无岗位 | 问清方向，同公司不同方向差异巨大 |
| 只有岗位无公司 | 跳过公司调研，只做 JD 解析 |
| 什么都没有 | 不做定制，先回到 Phase 1 建母版 |

**绝对不要替用户想象 JD 内容。** 编出来的 JD 会导出一份看起来很贴合、实际南辕北辙的简历。

---

## JD 原文快照（必须）

```yaml
jd_snapshot:
  source_url: https://...
  fetched_at: 2026-08-29T11:00
  text: |
    （JD 原文，逐字保存）
```

**为什么必存**：JD 会下线、会改。定制版必须能回溯到当时的 JD，否则三个月后用户看着自己的简历，不知道当初为什么这么写。

## P1 / P2 / P3 分层

| 层级 | 含义 | 来源 |
|---|---|---|
| **P1 critical** | 硬性门槛，没有基本过不了筛 | JD 中"要求""必须""X 年以上"部分 |
| **P2 important** | 重要加分项 | JD 中"优先""加分"部分 |
| **P3 nice-to-have** | 锦上添花 | JD 末尾的软性描述 |

### 分层依据

1. **出现位置**：JD 越靠前的要求越硬
2. **措辞强度**："熟练掌握" > "了解"；"要求" > "优先"
3. **重复次数**：正文和任职要求里都提到的，是核心
4. **横向对比结果**：同类岗位 JD 中出现频率高的（见下节）

### 输出格式

```yaml
analysis:
  p1_critical: [Go, 高并发系统设计, 分布式系统]
  p2_important: [Flink, 增长系统经验, MySQL 调优]
  p3_nice: [开源贡献, 大厂背景]
```

## 同类岗位 JD 横向对比（强烈建议）

**这是联网调研中收益最高、风险最低的一步。**

### 做法

1. 抓取 5-10 家同类公司的**同岗位** JD
2. 提取关键词，做出现频次统计
3. 按频次分层：

| 出现频率 | 判定 | 归入 |
|---|---|---|
| ≥ 8/10 | 行业通用硬性要求 | **P1** |
| 3-7/10 | 岗位方向常见要求 | **P2** |
| ≤ 2/10 | 该公司的个性化偏好 | **P2 末尾**（定制时的差异化抓手） |

### 为什么这一步特别值钱

- **零幻觉风险**：纯文本频次统计，不需要 LLM 发挥
- **比读单家公司官网收益高**：单家 JD 可能有噪音（HR 手抖写错、该岗位实际不招了），多家交叉才能得出真硬性要求
- **能识别"JD 骗人"**：某要求只在 A 公司出现、同行都没有 → 大概率是这家公司的特殊偏好或过时要求

### 差异化抓手

出现频率 ≤ 2/10 的要求最值得关注——**这正是定制的价值所在**。同行都要的大家都有，只有这家特别提的，才是你该在简历里突出的。

## 匹配打分

定制时按此打分选条目：

```
得分 = Σ(P1 命中 × 3) + Σ(P2 命中 × 2) + Σ(P3 命中 × 1)
     + 证据强度加成（verified +2, pending +0, inferred 不入选）
     - 无证据技能惩罚（-3）
```

排序后取前 N 条（N 由页数上限决定）。

**P1 未命中的关键词必须写进 `gaps`**，出片时明确告诉用户：
> "本版未覆盖岗位核心要求 X，你的母版里没有相关经历。建议补充，或在求职信中说明。"

不打分的匹配是玄学；打分但不可解释的匹配同样是玄学。**每一条选入的理由都要能说清楚。**

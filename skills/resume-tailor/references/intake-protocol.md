# 材料采集协议

## 为什么必须分轮

**一次甩一张大表，放弃率极高。** 详细模板是对的，但必须拆成轮次，每轮结束都要给用户可见的产出。

| 轮次 | 采集内容 | 用时 | 结束时的产出 |
|---|---|---|---|
| **R1 骨架** | 基本信息 + 经历清单（时间/机构/职位/一句话定位） | ~10 min | 母版 v1 + 一页时间线预览 |
| **R2 成就卡** | 逐条经历填卡，**一次只问一条** | 每条 3-5 min | 母版 v2，成就池成型 |
| **R3 补强** | 只对"高价值但 `evidence: pending`"的条目追问 | 按需 | 证据状态升级 |
| **R4 清账** | 出片前集中追问所有 `pending` | ~5 min | gaps 清空 |

R2 的关键：**一次只问一条经历**，问完立刻回显结构化结果让用户确认。不要连发五条。

---

## R1 骨架

```
1. 姓名 / 电话 / 邮箱 / 现居城市
2. 求职方向（一句话）
3. 经历清单（按时间倒序，每条只要一行）：
   - 起止时间 | 机构 | 职位 | 一句话定位
4. 教育背景
```

第 3 项只要一行。用户填"2023.04-至今 某某科技 后端工程师 做增长系统"就够，细节留到 R2。

拿到后就生成时间线预览给用户看——**让用户先看到东西**，后面的配合度会高很多。

---

## 采集的闭环：每轮都回到篇幅诊断

**采集不是线性流程，是带反馈的循环。** 每采集完一轮，立刻跑：

```bash
python scripts/density.py --person <姓名>
```

拿到「还差 N 行」后，按 `mining-playbook.md` §5 的优先级回问。
**不要让用户在没有反馈的情况下连答十几个问题** ——
把"你的简历从半页变成一页了"这个可见进展给他看，是配合度的唯一来源。

| density 报告 | 回问什么 | 依据 |
|---|---|---|
| 缺段（P1） | 有没有漏掉的经历/项目/兼职 | mining §4 材料源清单 |
| 漏采经历（P1） | 有没有"不算正式工作"但干过的事 | mining §3.10 通用兜底 |
| 补结果（P2） | 做完之后什么变了 | mining §2 线索追猎 |
| 补难点（P3） | 最卡的是哪一步 | mining §3 各职业族「难点」行 |

提问弹药一律从 `mining-playbook.md` 取，**不要用通用问题**。
「你取得了什么成绩？」的答案是「提升了效率」；
「月结对账原来几天、现在几天？」的答案才是素材。

## R2 成就卡（核心）

每条经历下逐条成就填写。六项，前五项必填：

```
【动作】你做了什么      → 重构 / 搭建 / 优化 / 设计 / 推动 / 排查 / 主导
【对象】作用于什么      → 归因链路 / 推荐召回模块 / 订单结算流程
【方法】用什么手段      → 引入 Flink 实时计算 / 重写调度策略 / 灰度+AB 验证
【结果】发生了什么变化  → 延迟 24h → 5min / 成本降 40% / 故障率 3%→0.2%
【边界】团队 vs 个人    → 团队 4 人，我负责 Flink 算子开发部分
【难点】为什么不是谁都能做 → 需在不中断服务前提下做双写迁移（选填，但最值钱）
```

### 为什么要有「边界」

90% 的简历注水发生在这里。团队成果写成个人成果，是最常见也最容易被拆穿的形式。

追问话术（用户答"我们做了 X"时）：
> "这个项目团队几个人？你具体负责哪一块？"

### 为什么要有「难点」

**这是最被低估的一项。** 结果可以注水，难点很难编——面试官追问三层时，编的结果会崩，编的难点崩得更彻底。

用户答不上"难点"时，换个问法：
> "这件事里，最让你头疼的是哪一步？如果换个人来做，他可能卡在哪？"

## 量化启发清单

用户最常见的回答是"提升了效率""优化了体验"。**不要接受**，按七个维度逐个试探：

| 维度 | 追问示例 |
|---|---|
| **规模** | 多少 QPS / DAU / 数据量 / 代码行数 / 服务数？ |
| **效率** | 耗时从多久变多久？频次从多少次变多少次？ |
| **质量** | 错误率、成功率、P99、评分、投诉量的变化？ |
| **钱** | 省了多少成本？带来多少收入 / GMV？ |
| **人** | 团队几人？带几个人？跨几个部门？ |
| **对比** | 改造前后？行业基准？历史最好水平？ |
| **范围** | 覆盖多少用户 / 城市 / 业务线？ |

**一次只问一个维度**，用户答不上就换下一个。七个都答不上，才标记 `pending` 走人。

---

## 证据三问

每个数字必问。三问过完，`evidence` 才能从 `pending` 升到 `verified`。

1. **这个数字从哪来？**
   系统报表 / 财务口径 / 估算 / 领导口头？
2. **是团队的还是你的？**
   你的贡献占比？
3. **面试时被追问三层，你答得上来吗？**

第三问是终极检验。答不上来的**保持 `pending`**，不要为了好看编一个。

---

## 提问预算（通用分发必须遵守）

用户不配合是常态，**不要纠缠**：

- 同一条经历最多追问 **3 轮**
- 用户说"不记得""没有数字""差不多吧""这个重要吗" → 立即标记 `pending`，继续下一条
- 用户明确表示不想答 → 跳过，写入 `gaps`，出片时统一提示

**用户的沉默不是授权让你编。**

追问时可以说明理由，提高配合度：
> "这个数字我问得细，是因为面试官大概率会追问。你如果说不清来源，我们先标成待补，等你确认了再补上——比直接写个数字安全。"

## 冷启动引导（用户只说"帮我做简历"时）

不要甩表格。先问三件事：

1. 目前（或最近）在做什么工作 / 项目？
2. 目标岗位或方向是什么？
3. 手边有没有旧简历、周报、绩效总结、项目文档可以丢过来？

**第三问最关键**——用户手上往往已有现成材料，只是没意识到能用。

### 可用的材料类型

| 类型 | 价值 | 注意 |
|---|---|---|
| 旧简历 | 高，结构完整 | 可能本身质量差，是"低质量源头" |
| 绩效自评 / 述职 PPT | **最高** | 天然含量化数字与贡献边界 |
| 周报 / 日报 | 中 | 碎片化，需按项目归并 |
| 项目文档 / 技术方案 | 中 | 技术细节多，业务结果少 |
| GitHub 贡献记录 | 中 | 可验证的硬证据 |
| 聊天记录 / 邮件 | 低 | 需人工提炼 |

**述职 PPT 是被严重低估的材料源。** 它天然包含"我做了什么 + 数字结果 + 团队分工"，且是用户自己写过、能背得下来的内容。

---

## L1 档位：从旧简历解析

用户给了旧简历时：

1. 解析出经历清单 → 生成 R1 预览 → 让用户确认有无遗漏
2. 对每条经历的每条 bullet 判定：`action/object/method/result` 是否齐全
3. 缺 `result` 的 → 走量化启发清单
4. 缺 `boundary` 的 → 走边界追问
5. **`raw_input` 存原文**，解析出的结构化内容单独存

注意：**旧简历常是低质量源头**。用户给的旧简历如果全是"负责 XX 工作"这种职责描述，等于没有成就——必须走 R2 补问，不能直接用。

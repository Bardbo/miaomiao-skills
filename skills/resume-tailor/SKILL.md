# 简历定制

帮用户把真实经历沉淀成一份可长期维护的**母版**，再从母版派生出**针对具体公司与岗位**的投递版本。

## 这个 skill 到底在做什么

**在不脱离真实描述的前提下，把简历写得更有竞争力，提高求职成功率。**

"高大上"不能靠编事实。它靠三种**不产生新事实**的手段：

| 手段 | 说明 | 例子 |
|---|---|---|
| **翻译** | 内部土话 → 行业通用术语，对接 JD 关键词 | "写了个日报表脚本" → "搭建项目运行数据自动化分析流程" |
| **聚焦** | 从"我做了什么活" → "我解决了什么问题" | "负责垃圾询盘识别" → "构建询盘质量分类模型，自动拦截无效询盘" |
| **层级提升** | 执行层描述 → 方案层描述 | "用 BERT 微调做分类" → "基于预训练语言模型的文本分类方案选型与落地" |

三者的共同点是**事实没变，读法变了**。这就是包装的合法空间，也是本 skill 的全部价值所在。

反过来说，任何"让它更好看"的操作，只要产生了母版里不存在的事实，就不是包装，是编造。

## 核心立场

**只筛选、不编造。** 母版里没有的东西，不会出现在任何定制版上。

---

## 适用范围（先确认，别跑偏）

**本 skill 的唯一交付物是简历本身。** 任何不以"产出一版更好的简历"为目标的工作，都是偏航。

### ✅ 在范围内

| 场景 | 说明 |
|---|---|
| 梳理零散经历 | 把流水账/旧简历/口述整理成结构化母版 |
| 优化与润色 | 改写法、去 AI 味、强化量化与抗追问能力 |
| 按岗位定制 | 依据真实 JD 做条目筛选、排序、侧重 |
| 出片 | 渲染成可投递的 docx / PDF |
| 自检 | Gate 链、反向面试、缺口清单 |

### ❌ 不在范围内 —— 这些是别的事，不要占用主线

| 场景 | 为什么不在范围内 |
|---|---|
| **考公 / 考编 / 事业单位统考** | 流程是**报名 + 笔试 + 面试**，**全程不投简历**。为它做简历分析是无效功 |
| **岗位检索 / 雇主地图 / 渠道汇总** | 那是求职顾问的活。可作为附属产出放在 `strategy/`，但**不得反过来驱动母版结构** |
| 面试辅导、薪资谈判、Offer 比较 | 相邻但独立。离职口径、涉密红线这类**直接影响简历文本**的除外 |
| 职业规划 | 只接收结论（"我要安稳岗"），不代为规划 |

### 判断口诀

> **这一轮做完，简历文件变好了吗？**
> 变了 → 在范围内。没变 → 停下来，回到母版或定制版。

**一个常见陷阱**：用户给了很多岗位、公司、薪资信息，AI 就顺着去分析"该投哪家"。这些信息的正确用途只有一个——**反推简历该怎么定制**（突出什么、淡化什么、语气如何），而不是去评估岗位好坏。

---

## 核心原则（不可协商）

1. **不编造事实、数字、职位、时间。** 信息不足时标记 `【待补】`，绝不自行补全一个"合理"的值。
2. **区分团队成果与个人贡献。** 团队 4 人的项目，不能写成"主导"。
3. **推断类信息不进简历正文。** 联网调研得出的中低置信信息只影响排序、语气与篇幅。
4. **用户是事实的唯一来源。** AI 可以追问、可以质疑、可以建议，但不能替用户回答事实问题。

违反上述任一条的输出，比不输出更糟——用户会拿着编造的内容去面试，一问就崩。

## 工作流总览

```
Phase 0 冷启动      → 判断材料档位，选采集路径
Phase 1 母版构建    → R1 骨架 → R2 成就卡 → R3 补强 → R4 清账
Phase 1.5 篇幅校准  → density 诊断 → 不够就回挖掘，够了才往下走
Phase 1.8 润色      → bullet 体检 → 补五要素 → 三候选改写
Phase 2 岗位解析    → JD 快照 + P1/P2/P3 分层 + 同类岗位横向对比 + 公司调研
Phase 3 选择改写    → 按 JD 打分选条目 → L1/L2/L3 三层改写
Phase 4 Gate 链     → G1-G6 六道检查，不过打回
Phase 4.5 内容质量人审 → 堵「闸门全绿但成品差」：机械自检 C1-C6 + 人审 H1-H4，不过不进出片
Phase 5 出片        → 渲染 → 实测页数 → 残页必须处理
Phase 6 回流提案    → AI 提议 → 用户裁决 → 母版升版
Phase 7 模拟面试    → 出片后主动问 → 基于成稿+JD 出题（只筛选不编造）
```

每个 Phase 的详细规则见 `references/`。**不要跳过 Phase 1 直接做定制**——没有母版的定制等于每次从零开始，且无法防造假。

## 三段式：先有量，再有质，再有针对性

**一份好简历要连过三关，顺序不能颠倒。**

| 关 | 问题 | 工具 | 不过关的表现 |
|---|---|---|---|
| **① 量** | 素材够不够撑满一页 | `density.py` | 成稿只有半页，或两页但第二页空一半 |
| **② 质** | 每条 bullet 说清了吗 | `polish.py` | 全是「负责 XX 工作」，L2 以上占比 < 60% |
| **③ 针对性** | 有没有对准这个岗位 | Phase 2–3 | 内容都对，但跟 JD 对不上 |

**大多数"简历很 low"的抱怨，根因在第 ① 和第 ② 关，不是措辞问题。**
一页写不满的简历，润色到天上去也还是不满；
全是职责型 bullet 的经历段，换个动词还是职责型。

**所以：先跑 density，再跑 polish，最后才谈定制。**
顺序反了会做大量无用功——把一份只有半页、全是空话的简历精心定制给某个岗位，
结果是一份只有半页、全是空话的定制版。

## 两个前置参数：profile 与 polish

动手前必须先定这两个参数。它们**正交**，且都**不能解锁 evidence 限制**。

| 维度 | 管什么 | 取值 | 存在哪 |
|---|---|---|---|
| **`profile`** 人群画像 | 写什么——保留哪些素材、段落顺序、技能收敛度 | `campus` / `junior` / `experienced` / `expert` | `preferences.profile` |
| **`polish`** 包装级别 | 怎么写——同一事实说到几成 | `sincere` / `balanced` / `bold` | `preferences.polish` |

**profile 是筛选器，polish 是放大器。** 放大器不能放大没被选中的东西。

### profile：人群与阶段画像

不同画像的简历几乎不是同一种文体。把社招简历写成校招格式，和把校招简历硬撑成社招格式，都是灾难。

| profile | 判断依据 | 教育段 | 校园内容 | 技能段 | 篇幅 |
|---|---|---|---|---|---|
| `campus` 校招 | 应届 / 实习 / 毕业 <1 年 | **置顶** | 保留（学生工作、竞赛、GPA） | 可全列，无佐证也允许 | 1 页 |
| `junior` 初级 | 1–3 年 | 次位 | 只留高含金量，删学生工作 | 收敛到有佐证 + 相关 | 1 页 |
| `experienced` 社招 | 3 年+（**默认**） | **沉底** | **全部删除** | 只留有佐证，≤10 项 | 1–2 页 |
| `expert` 资深 | 8 年+ 或有代表作 | 沉底一行 | 删除 | **不列技能清单**，能力写进经历 | 2 页内 |

**社招不写学生工作，不是因为它假，是因为它稀释信号。** HR 只关心"你能在我的岗位上立刻产出什么"，一条"曾任学生会部长"占掉的那行空间，本可以放一句能证明你能干活的话。校招反之——这时候校园内容就是主战场。

**技能堆叠是负分项。** 21 项技能里 13 项找不到项目佐证，HR 读到的不是"懂得多"，而是"泛而不精"。社招硬指标：≤10 项、每项都能在某条 bullet 里找到对应、过时技术用 `status: archived` 归档而非删除（母版是超集，换方向时要能复活）。

### polish：包装级别

| 级别 | 动词 | 上位概括 | 能力命名 | 缺失数字时 |
|---|---|---|---|---|
| `sincere` 真诚 | 用本人原话，不升级 | 禁止 | 禁止 | 留空 |
| **`balanced` 适度包装**（**默认**） | 升到**证据支持的最高级** | 允许一次 | 允许 | 用定性表述替代 |
| `bold` 酥化 | 主动叙事重构，成果前置 | 允许多次 | 允许 | 允许合理外推（须标注） |

**"证据支持的最高级"是核心约束**——能升到哪一级取决于证据，不取决于你想要多好看。4 人团队里做了一个模块不能写"主导项目"；接手别人搭了一半的系统不能写"从 0 搭建"。

**两条硬规则：**

1. **polish 不能解锁 evidence。** `pending` 在 `bold` 下同样隐藏——强化包装无证据内容等于编造。
2. **polish 越高，G5 越严。** `bold` 下每个 bullet 要扛 5 层追问（其余 3 层），扛不住就回落到 `balanced` 表述。说得越漂亮，被追问得越狠。

### 技能表达范式：别写成工具清单

**收敛管"列几项"，范式管"该不该列"。** 范式是更上游的问题——一个能力若已商品化，就算技能段只有 3 项，列它也是浪费。

**核心判断：装个工具、问一句 AI 就能获得的能力，写在简历上没有区分度。**

2026 年的 SQL、RAG、多数框架都是这样。它们是真的，但已经是行业基线——基线能力单列，等于在简历上写"熟练使用搜索引擎"。不假，但没有信息量，还会让整段技能被读成"凑数"。

`kind` 三值，写进母版，渲染器强制执行：

| kind | 定义 | 行为 |
|---|---|---|
| `commodity` | 人人可得（SQL、RAG、多数框架） | **不单列**，藏进交付物 bullet 的 `tech_tags` |
| `capability` | 能独立从 0 做到 1 并交付给人用 | 主战场，必须有 `evidence_refs` |
| `leverage` | 放大产出效率（AI 原生、受限环境交付） | 放进 `ai_native` 段 |

> **`commodity` 不是"假"，是"没区分度"。** 它应该藏进交付物里——
> 写"搭建了自助查询平台"比写"熟悉 SQL"强得多，而 SQL 一个字都不用出现。

**AI 时代最反直觉的一条**：当所有人都在用 Copilot 时，"会用 AI"已经没有区分度；
反过来，**"把 AI 拿走，你还能不能交付"变成了强信号**——它证明能力是内化的，不是外包给工具的。
受限环境（内网、涉密、无云）下的独立交付，在 2026 年是稀缺品。

| 老土写法 | 新写法 |
|---|---|
| 熟悉 SQL | 删掉——写"搭建自助查询平台，交付后业务同事直接使用" |
| 熟悉 LangChain / RAG | 删掉——改说用 AI 工具链交付了什么 |
| 会用 AI 写代码 | 以 AI 辅助开发为主要工作方式，独立完成 X |
| 熟悉 Python | 挂到交付物——语言不是卖点，用它做出来的东西才是 |

完整规则、判断问句、转换表见 `references/rewrite-rules.md` → 「技能表达范式」。

### 「low 感」禁用清单：这一节背下来

**"整体简历显得很 low" 是本 skill 必须规避的失败模式。** low 不等于写得不好、也不等于内容不行，
它的准确含义是：**读起来像一个不会写简历的人写的** —— 事实可能全是真的，但每处细节都在告诉对方
"我没有更硬的东西可放了"。

判定口诀：**这一条，是让对方更想面试我，还是让对方看出我没东西可写？** 答不上来就是后者，删。

每条都已落进渲染器/校验器，不是靠自觉：

| low 写法 | 处理 |
|---|---|
| 技能后跟「（熟悉）」「（精通）」 | **成稿不显示**。自评不可查证；「熟悉」在 HR 眼里 ≈ 不精，越描越黑。`level` 只留在母版内部用于收敛 |
| 荣誉段只剩「优秀团员」这类 | **整段消失**。没有硬通货（竞赛名次 / 政府行业奖 / 奖学金级别）时，不存在的段落比一段弱荣誉强得多 |
| 技能按「编程语言 / AI 框架 / 人工智能」分类 | 改成**能力域**：算法与建模 / 工程与交付 / 智能交通与仿真 / AI 原生工作流 / 本地模型与生成 |
| 单列工具名（PyTorch、ComfyUI、llama.cpp） | 降级为注脚：`BERT 微调（PyTorch / Transformers）`。关键词仍在，但主句是能力 |
| 一行只有一个词的分组 | 同组至少 2 项，或改写为能力陈述 |
| 方法段用「、」平铺六七个动作 | 改成「→」串联：数据集构建 → BERT 微调 → 部署上线 → 监测维护 |
| 同一所学校拆成本硕两块 | 自动合并，学位各占一行 |
| AI 能力单独开段 | **并入专业技能**（`ai_native.group`）—— 单独开段等于宣告 AI 能力和专业能力是两回事 |
| 成稿里出现「待确认」「待补」 | `pending` 在 final 模式隐藏；摘要里出现占位符是 ERROR |
| 「熟练掌握 Office」「抗压能力强」 | 不写 |

完整清单与理由见 `references/rewrite-rules.md` → 「『low 感』禁用清单」。

### 摘要：社招最强去 low 手段，但默认关闭

没有摘要的社招简历，HR 要读完四段经历才能拼出画像——大多数人不会读那么久。三行摘要能让首屏立刻成立。

**但它默认 `summary.enabled: false`**：它是全篇唯一会新增**概括性表述**的段落，只能由已确认事实组成，
且须本人确认。校验器会拦截摘要里出现的 `pending` 内容与占位符。

### 求职意向不写进简历

默认不渲染"求职意向"。招聘系统里已有投递岗位，简历里再写既占首屏黄金位置，又暗示"海投 / 没想好"。

**目标岗位的正确载体是：文件名 + 投递邮件正文 + 打招呼语**，不是简历正文。

需要时（内部转岗、猎头推荐）可置 `show_intention: true`。

## Phase 0：冷启动

**第一步先定 profile。** 判断依据是工作年限与求职阶段（校招 / 社招 / 资深），不是年龄也不是职级。判断错了后面全白做——用校招格式写给 5 年经验的人，和用社招格式写给应届生，都是废稿。

拿不准就按年限默认：毕业 <1 年 → `campus`；1–3 年 → `junior`；3 年以上 → `experienced`；8 年以上或有代表作 → `expert`。

**polish 默认 `balanced`。** 用户没提就别问，直接用默认档。只有用户明确说"我想要真诚一点"或"你尽管包装"时才改。

**第二步判断材料档位**，不同档位走不同路径：

| 档位 | 特征 | 路径 |
|---|---|---|
| **L2 充足** | 用户给了详细材料（多段经历描述 + 数字） | 直接解析入库，跳到 R3 补强 |
| **L1 中等** | 有一份旧简历或一段连续描述 | 解析结构化 → 生成 gaps → R2 逐条补问 |
| **L0 贫瘠** | 只有一句"帮我做简历"或极简信息 | 进入引导式最小采集，见下 |

**L0 处理**：不要甩表格。先问三件事，拿到就有东西可干：
1. 目前（或最近）在做什么工作/项目？
2. 目标岗位或方向是什么？
3. 手边有没有旧简历、周报、绩效总结、项目文档可以丢过来？

第三问最关键——**用户手上往往已经有现成材料，只是没意识到能用**。

材料可以是任意格式（docx / pdf / md / txt / 直接粘贴 / 截图）。原件放 `people/<姓名>/sources/`，永不修改。

PDF 解析：用隔离环境的 PyMuPDF。**路径必须动态取，禁止硬编码任何用户名**——
换台机器就断，这是本项目踩过的坑：
```
# Windows（隔离 venv）
%USERPROFILE%\.workbuddy\binaries\python\envs\default\Scripts\pip.exe install pymupdf
# macOS / Linux
~/.workbuddy/binaries/python/envs/default/bin/pip install pymupdf
```

**统一解释器**：本机全流水线已验证可用的是
`~/.workbuddy/binaries/python/envs/default/Scripts/python.exe`（已装 PyYAML / python-docx）。
缺依赖就 `pip install PyYAML python-docx`，不要用系统 Python 凑合。
提取前先判断是文本型还是扫描型（`page.get_text()` 有内容即为文本型）。扫描型需要 OCR，成本另议。

**关键提醒**：从旧简历导入的内容属于**本人陈述**，不是第三方验证。一律标 `self_reported`，不要因为"这是用户自己写的"就默认标 `verified`——旧简历里同样可能有注水，而且它往往是低质量源头。

## Phase 1.5：篇幅校准（写满一页不是玄学）

**一份简历应该详实写满一页 A4，最多两页。** 这是可计算的，不是靠感觉。

```bash
python resume-tailor/scripts/density.py --person <姓名>            # 估算，秒出，采集过程中反复跑
python resume-tailor/scripts/density.py --person <姓名> --measure  # 实测，出片前跑一次（需先 render）
python resume-tailor/scripts/measure_pages.js people/<姓名>/output/resume-final.html
```

### 容量基准（由 A4 排版参数推出，已用浏览器实测校准）

| 项 | 值 |
|---|---|
| 正文区 | 174mm × 267mm → **42 行/页** |
| 每行 | 约 **46 个汉字** |
| 扣掉抬头（3.5 行）与页脚 | **净 36 行** |
| 一条理想 bullet | **约 2 行 ≈ 90 字** |
| 一页能放 | **7–10 条 bullet + 技能/证书/教育段** |

### 三种不合格状态

| 状态 | 判据 | 怎么办 |
|---|---|---|
| **不足** | 单页填充 < 88%（社招 85%） | 回 `mining-playbook.md` 补素材 |
| **残页** | 多页，但末页填充 < 55% | **二选一**：砍回上一页，或补满这一页 |
| **溢出** | 超过 profile 页数上限 | 收敛：砍与 JD 无关的 bullet |

### 残页是比内容少更糟的状态

1.4 页的简历打印出来是两页，第二页只有三行。
HR 翻过来读到的不是"这人经验丰富"，而是"这人没东西可写"。

**残页没有第三条路**——要么砍到 1 页，要么补满 2 页。把选择权给用户，不要自己决定。

### 目标页数由素材量决定

profile 只给**上限**，不给目标。让一个只有 3 条 bullet 的人"补到 2 页"，
这个建议不会被执行，只会让人放弃。素材只够一页，就先交付一页。

## Phase 1.8：润色（把说清的再说好）

**润色的前提是素材已经说清了。** 一条"负责 XX 工作"改十遍还是"负责 XX 工作"。

```bash
python resume-tailor/scripts/polish.py --person <姓名>             # 全量体检
python resume-tailor/scripts/polish.py --person <姓名> --only L0   # 只看最该回炉的那些
```

### Bullet 四级（详见 `references/polish-playbook.md`）

| 级 | 定义 | 处理 |
|---|---|---|
| **L0 职责型** | 只说"负责什么" | **回采集，润色无能为力** |
| **L1 行动型** | 说了怎么做，没说结果 | 补 result |
| **L2 结果型** | 有变化，无难点 | 补 difficulty + 影响范围 |
| **L3 影响型** | 结果 + 影响 + 难点 | 只调措辞 |

**目标：L2 以上 ≥ 60%，至少 1 条 L3。**

### 改写三候选

改写不是替用户决定。**每次给 3 个候选，附理由与风险，默认推荐中间档。**

最激进的那个通常也是面试时最容易崩的那个——所以只推荐，不代劳。

### 硬边界

1. **润色不产生事实。** 缺 result 的正确动作是去问用户，不是在句尾加个数字。
2. **润色不升级 evidence。** `pending` 改十遍还是 `pending`。
3. **润色不覆盖 `raw_input`。** 改写结果放 `rewrite_candidates`。

## 多人母版（people/ 目录约定）

本 skill 可同时维护多个人的母版，每人一个目录，**互不干扰**：

```
people/
  _template/               模板，复制用，不改动
    master.template.yaml
    tailored.template.yaml
  张三/
    master.yaml            母版 —— 唯一事实源
    master.preview.md      只读预览（自动生成，勿手改）
    sources/               原始材料存档，只追加不修改
    targets/<公司>-<岗位>/ 按岗位定制（tailored.yaml，JD 原文存进 target.jd_snapshot.text 字段）
    output/                出片产物
```

> **路径约定（包 / 工作区分离，重要）**
> - **包根 `resume-tailor/` 自包含**：`scripts/`、`config/`、`assets/`、`references/` 全在包内，脚本按**自身文件位置**自解析 —— 包整体拷到任何机器都能跑。
> - **`people/` 是用户数据，不进包**：脚本从**当前工作目录**找 `./people`；也可用环境变量 `RESUME_WORKSPACE` 指向别处的工作区。
> - 因此：在**含 `people/` 的工作区目录**里执行命令，用 `resume-tailor/scripts/xxx.py`（相对或绝对路径）调用脚本。
> - 这样设计的好处：**升级 / 重装 skill 不会冲掉客户简历**，且一份 skill 可同时服务多个工作区（换目录即换客户群）。
> - 所有脚本均以路径作为参数传入，不把他人母版路径写死。

**统一入口**（`--person` 省略时，若只有一个人则自动选中）：

```bash
python resume-tailor/scripts/resume.py people                      # 列出所有人及母版版本
python resume-tailor/scripts/resume.py new     --person 张三        # 从模板创建新人
python resume-tailor/scripts/resume.py check   --person 张三      # 校验（G1/G2/G4）
python resume-tailor/scripts/resume.py lint    --person 张三      # 只扫中文 AI 味
python resume-tailor/scripts/resume.py preview --person 张三      # 生成 Markdown 只读预览
python resume-tailor/scripts/resume.py render  --person 张三 --mode draft|final

# 篇幅与润色（Phase 1.5 / 1.8）
python resume-tailor/scripts/density.py --person 张三             # 篇幅诊断（估算）
python resume-tailor/scripts/density.py --person 张三 --measure   # 篇幅诊断（浏览器实测）
python resume-tailor/scripts/polish.py  --person 张三             # bullet 体检与改写方向

# 按岗定制（Phase 3 → 出片）
python resume-tailor/scripts/analyze_jd.py people/_jd/J1-校招技术.md --master people/张三/master.yaml --emit targets/xxx/analysis.yaml  # JD 分层 + 母版缺口（片段粘贴进 tailored.yaml 的 target.analysis）
python resume-tailor/scripts/check_gates.py \
    --master people/张三/master.yaml \
    --target people/张三/targets/方向A-技术向/tailored.yaml \
    --rendered people/张三/output/resume-方向A-技术向-draft.html   # G1 溯源 / G2 证据 / G3 覆盖 / G4 去 AI 味（硬校验）

# 出片：HTML → 带文字层的 .docx（ATS 可解析）
python resume-tailor/scripts/export_docx.py --person 张三                       # 通用版
python resume-tailor/scripts/export_docx.py --person 张三 --target targets/方向A-技术向/tailored.yaml --mode draft  # 定制版（命名与 render 一致）
# 直接指定 HTML 也可：python resume-tailor/scripts/export_docx.py --html people/张三/output/resume-final.html

# 出片：HTML → 带文字层的 .pdf（ATS 可解析，复用已装 node playwright + chromium）
python resume-tailor/scripts/export_pdf.py --person 张三                       # 通用版
python resume-tailor/scripts/export_pdf.py --person 张三 --target targets/方向A-技术向/tailored.yaml --mode draft  # 定制版
# 直接指定 HTML 也可：python resume-tailor/scripts/export_pdf.py --html people/张三/output/resume-final.html
```

> **出片格式事实**：`docx` 与 `pdf` 均已真实可用，都解析 render 产物 HTML 导出（所有筛选/隐藏规则经 render 单一来源生效），**都带文字层、ATS 可解析**。
> - `docx`（`scripts/export_docx.py`）：纯 Python，解析 HTML → Word，可二次编辑。
> - `pdf`（`scripts/export_pdf.py` → `scripts/export_pdf.js`）：用真实浏览器按简历自带 @page A4 + 分页 JS 打印，版式与屏幕/出片 HTML 完全一致；依赖隔离工作区已装的 node playwright + chromium（见 `density.py --measure`）。
> 不要交付 HTML 截图 PNG，它没有文字层、ATS 解析不了。

直接调用底层脚本也可以，但别把别人的母版路径写进文档或脚本默认值——**路径硬编码是多人场景下最容易出的事故**。

跨人共享的配置放根目录 `config/`（禁用词表、技术词词典），不随人复制。

## Phase 1：母版构建

四轮采集，**每轮都要有可见产出**，详见 `references/intake-protocol.md`。

- **R1 骨架**（~10 min）：基本信息 + 经历清单 → 母版 v1 + 时间线预览
- **R2 成就卡**：逐条经历填卡，**一次只问一条**
- **R3 补强**：只对高价值但 `evidence: pending` 的条目追问
- **R4 清账**：出片前集中追问所有 `pending`

母版数据结构见 `references/schema.md`，模板见 `people/_template/master.template.yaml`。

> **⚠ 改 schema 必须一次同步 5 处 —— 这是本项目踩过 4 次的坑。**
> 只改一处会导致"母版里有、成稿里没有"的**静默丢失**，比报错更难发现。
>
> | # | 位置 | 改什么 |
> |---|---|---|
> | 1 | `references/schema.md` | 字段定义与示例 |
> | 2 | `people/_template/master.template.yaml` | 新建母版时的模板 |
> | 3 | `resume-tailor/assets/master.template.yaml` | skill 自带模板（同上） |
> | 4 | `scripts/validate_master.py` | `check_master()` 校验 + `render_preview()` 预览 |
> | 5 | `scripts/render_resume.py` | 实际渲染 |
>
> 新增字段后立刻做全量回归：`check` → `preview` → `render --mode final/draft` → 两个方向定制版。

**关键字段 `evidence`** —— 这是数据字段而非提示词，它会一路渲染到最终产物上，逼着用户去补，而不是让 AI 悄悄编一个合理数字。

| 档位 | 含义 | 能否进简历 |
|---|---|---|
| `verified` | 有第三方可查证证据（专利号 / 论文 / 公开记录） | ✅ 强主张可保留 |
| `self_reported` | **本人明确陈述**（旧简历、口述、回答） | ✅ 可写，但**不降级**；强主张会提示"面试必追问" |
| `pending` | 信息不全，等待补充 | ⚠️ 出片隐藏，宁缺毋滥 |
| `inferred` | AI 推断 | ❌ 禁止进入母版 |
| `unusable` | 证据存在但不可对外（权属归他方 / 涉密） | ❌ 禁止进入任何定制版 |

**`self_reported` 与 `verified` 的区分很重要**：用户自己写的东西不是"已验证"。旧简历里同样有注水，而它是很多低质量内容的源头。二者待遇也不同——前者不降级（那是用户的话，改它是篡改而非防造假），但强主张会提醒面试风险。

**`unusable` 是真实场景里高频的一档**：在职期间的职务发明（专利/软著归公司）、涉密项目、签了保密协议的工作——证据确实存在，但拿出来会出问题。这类条目加 `acknowledged: true` 可把重复的 ERROR 降为 INFO（表示"已知晓，仅存档"），但**仍然不会出现在任何出片里**。

`unusable` 最常见的连带后果：某段经历的核心产出被判不可写后，整段会变得几乎没内容可写。这时不要去"找补"，应如实压缩篇幅，并在 `content_gaps` 里记录。

### 提问预算（通用分发必须遵守）

用户不配合是常态，不要纠缠：

- 同一条经历最多追问 **3 轮**
- 用户说"不记得""没有数字""差不多吧" → 立即标记 `pending`，继续下一条
- 用户明确表示不想答 → 跳过，写入 `gaps`，出片时统一提示

**用户的沉默不是授权让你编。**

## Phase 2：岗位解析

需要用户提供：目标公司 + 岗位名称 + JD 原文（或链接）。

1. **JD 原文快照**：逐字存进 `target.jd_snapshot.text` 字段（结构见 `references/schema.md` 的 `target` 段）。JD 会下线，定制版必须能回溯原文。
2. **P1/P2/P3 分层**：P1 核心硬性要求 / P2 重要加分 / P3 锦上添花。
3. **同类岗位横向对比**（强烈建议）：抓 5-10 家同类公司同岗位 JD 做关键词交叉统计。出现 8/10 的是真硬性要求。这一步是纯文本统计，几乎零幻觉风险，比读单家公司官网收益高得多。
4. **公司调研**：见 `references/company-research.md`。置信度分高/中/低，只有高置信能进正文。

用户只给公司不给 JD → 引导其提供，或标注"未获得 JD，本版按通用岗位要求定制"，**不要替用户想象 JD 内容**。

## Phase 3：选择与改写

**选择优于创作。** 定制版 = 母版版本号 + 条目 ID 列表 + 改写策略，不存内容副本。

四层改写，风险递增：

| 层 | 操作 | 默认 |
|---|---|---|
| L1 | 排序——调整经历与 bullet 顺序 | 开 |
| L2 | 裁剪——隐藏无关条目 | 开 |
| L3 | 侧重——同一事实换个说法与重点 | 开 |
| **L4** | **新增——写母版里没有的内容** | **硬 Gate 拦截** |

L4 触发时的正确动作不是"写了它"，而是**把缺的东西作为新条目加进母版并标记 `pending`**，让用户去补。

中文写作规范、AI 味禁用词见 `references/rewrite-rules.md` 与 `assets/forbidden_terms.txt`。

---

## Phase 4：Gate 链

出片前必过，任一 Gate 不通过则打回重写。详见 `references/gate-checklist.md`。

| Gate | 检查 | 失败处理 |
|---|---|---|
| G1 溯源 | 每个 bullet 能否追到 master 条目 ID | 追不到 = L4 违规，打回 |
| G2 证据 | `pending`/`inferred` 是否写成确定语气 | 降级为"参与"或标 `【待补】` |
| G3 覆盖 | P1/P2/P3 关键词在**成稿**中的命中率（优先测 `--rendered` 真实 HTML，无则回落母版文本） | 未命中的写入 gaps 提示；P1 缺失=硬伤，改写解决不了 |
| G4 去 AI 味 | 禁用词 + 句式检查 | 强制改写 |
| G5 反向面试 | 每个 bullet 追问三层扛得住吗 | 扛不住的降级或删除 |
| G6 版式 | docx/PDF 渲染检查 | 版式不合格打回 |

**G5 是最有效的一道**：改完立刻假设自己是面试官追问一遍，扛不住的 bullet 就不该留。

静态可检查的部分（G1 溯源 / G2 证据 / G3 覆盖 / G4 去 AI 味）用 `scripts/check_gates.py` 做硬校验——写在提示词里的规则会被 LLM 绕过，写在脚本里的不会。

> **`check_gates.py` 历史事故（已修复）**：旧版按"加法白名单"理解 `selection`（期待 `experiences`/`achievements` 是选中列表），而 `render_resume.py` 实际按"减法黑名单"实现（`hidden_achievements`/`hidden_skills` …）。两者对不上，G1 遍历到 0 个条目——闸门恒真，17 个警告照样判"通过"，防造假防线形同虚设。现版复刻 render 的真实筛选语义，先算"生效条目集"再校验；被引用的 ID 若母版里没有一律 ERROR（拼错的 ID 在减法语义下会静默失效，必须拦住）。G3 原从未实现，现版已补齐。

## Phase 4.5：内容质量人审（堵「闸门全绿但成品差」）

**触发时机**：Phase 4 Gate 链通过之后、Phase 5 出片之前。每次出片（含回流后重新出片）都要过。

**为什么需要它**：Gate 链（G1–G6）覆盖结构 / 证据 / 覆盖 / 去 AI 味 / 版式，拦得住"编造、漏源、AI 味、版式崩"，但拦不住"内容差"。实证：2026-09-22 示例客户→某科技公司副总经理岗 出片时 `GATES_EXIT=0`（六道全过），用户看后判"成品很差"——开源选项太弱、写了 star、写了「涉密项目」、缺乏对口含金量。其中 star/涉密 已由渲染器 + G4 兜底，但**开源对口度、量化率、摘要呼应 JD、整体观感**这几类"内容质量"问题，自动化闸门够不到，必须有一道独立的**人审**。

**两层检查，缺一不可**：

1. **机械自检（C1–C6）**：AI 读渲染后的 final HTML 自动判 PASS/FAIL——开源不写 star、涉密零字样、开源筛强留弱、量化补全、摘要呼应 JD、去 AI 味超出词表。详见 `references/content-quality-review.md` 第一节。
2. **人审提示（H1–H4）**：AI 给不出判断、必须让用户过目的 4 问——内容对口度 / 含金量诚实度 / 市场匹配 / 整体观感。出片前用 AskUserQuestion 或普通提问抛给用户，任一项说"不对"就打回改。

**输出形态**：出片前给出「内容质量人审报告」（机械项 PASS/FAIL + 人审待裁决 + 结论），机械项全过且人审用户签字后才进 Phase 5。报告模板与逐条判据见 `references/content-quality-review.md`。

> **不要把它降级成"提示词里写一句"**：H1–H4 是用户的主观判断，脚本替代不了；C1–C6 里能机械判的已下沉为渲染器 + G4 兜底（防回归），剩下的必须由 AI 在出片前**真的跑一遍**并等用户裁决，而不是默默跳过。

## Phase 5：出片

默认 docx（可编辑，招聘系统兼容性最好）。用户要求时出 PDF。

渲染前先生成 Markdown 预览给用户确认内容，确认后再出片。

## Phase 6：回流提案

定制过程中产生的好表述，AI 提议回流母版，**用户裁决**。三类分流：

| 类型 | 说明 | 处理 |
|---|---|---|
| **A 事实新增** | 用户新提供的事实 | 建议回流，低风险 |
| **B 表述优化** | 同一事实的更好说法 | 回流，但**不覆盖 `raw_input`** |
| **C 推断填充** | AI 为贴合 JD 补的内容 | **禁止回流，闸门焊死** |

C 类闸门必须焊死的理由：用户到第 5 次裁决时，已经记不清哪些是自己说的、哪些是 AI 编的。

每条提案必须包含：类型 / 位置 / 原文 / 建议 / **AI 判定理由** / 风险 / 三选一动作（采纳 / 拒绝 / 改后采纳）。**AI 只给建议，不自动执行。**

母版升版后，扫描所有引用旧版本的定制版，标记"建议重新生成"。

## Phase 7：模拟面试（出片/回流后主动询问）

**触发时机**：Phase 5 出片完成（且 Phase 6 回流裁决完毕）后，AI 必须**主动抛出一个确认问题**，问用户要不要基于这份成稿（母版 + 定制版 + JD）模拟几个面试问题来练手。不要默默结束，也不要等用户自己提。

**为什么放在这里**：此时简历内容已锁定、与 JD 已对齐，正是"用这份简历去面试"的真实场景起点。趁热打铁练一轮，比事后另开对话更顺。

**无 JD 也能用**：若这次只出了母版/通用版、没有 JD，则跳过"技术类对齐 JD"那部分，只出行为类（基于成就卡）+ 基于成稿技能段的专业题，并在反向压力类里标注"无 JD 可对照，按成稿自身薄弱点出题"。

### 交互约定

1. **先问一句，给选项**：用 AskUserQuestion / 普通提问给出「要 / 不要 / 只看某类」三档，让用户选，不要默认直接开练。
2. **用户选"不要"**：礼貌收尾，不纠缠、不二次推销。
3. **用户选"要"或"只看某类"**：进入下方生成规则。

### 生成规则（同样遵守"只筛选、不编造"）

模拟面试的本质是**把成稿里已经写明的证据，变成面试官会追问的角度**——问题必须能在简历/JD 里找到出处，绝不能凭空捏造一段经历来出题。详细玩法（题源、三类题型模板、配比、输出格式、陪练反馈、禁止清单）见 **`references/interview-prep.md`**。要点：

- **题源唯一**：只从「成稿 HTML / 母版 YAML / JD 文本」里已有的事实出题，每条题标注对应成稿哪一段。
- **三类题型**：行为类（STAR，针对成就卡）/ 技术专业类（针对 JD 的 P1 + 成稿技能段）/ 反向压力类（来自 G5，把 Gate 薄弱点变追问）。
- **数量**：默认 3–5 题（行为 2 + 技术 1–2 + 反向 1），用户可要更多或只要某类。
- **每题带"考察点 + 理想回答锚点"**：锚点只列成稿里**已有**的事实，不替用户编答案。
- **禁止**：编造简历里没有的项目、数字、公司；不把 `pending`/推断填充当既定事实出题而不加提示。

### 输出形态

直接在一次回复里给出「问题清单 + 每题考察点 + 锚点」，然后**等用户逐题口述回答**；用户答后可切到"陪练反馈"模式：对照成稿事实指出回答里哪些有支撑、哪些在发挥、哪些与 JD 的 P1 对齐。全程不修改成稿（改内容走 Phase 6 回流）。

---

## 降级路径（用户不配合时）

材料残缺不是拒绝服务的理由，但产出必须诚实标注：

- `gaps` 清单随成品一起交付，明确列出"这些信息缺了，补上会让简历强很多"
- 因 `pending` 而被降级的 bullet，在预览里标灰并注明原因
- 宁可交付一份**短而实**的简历，也不交付一份**长而虚**的

## 边界（明确不做）

- ❌ 不自动投递、不批量海投
- ❌ 不编造经历、数字、时间、职位
- ❌ 不把团队成果包装成个人主导
- ❌ 不把"计划中/学习中"写成"已完成/精通"
- ❌ 不用推断的公司信息冒充已知信息

### 出片环节的防造假规则（render_resume.py 已实现）

| evidence | 校对模式 | 出片模式 |
|---|---|---|
| `verified` | 正常渲染 + ✔ | 正常渲染 |
| `self_reported` | 正常渲染 + ○本人陈述 | 正常渲染（不降级） |
| `pending` | 强主张动词降级 + 【待补】标记 | **隐藏**（宁缺毋滥） |
| `inferred` | 拦截 | 拦截 |
| `unusable` | 拦截 | 拦截 |

**这张表不受 profile / polish 影响。** 画像只决定保留哪些素材，包装只决定说到什么程度，两者都不能让 `pending` 变成可写、让 `unusable` 变成可发。

### 出片环节的人群与包装规则（render_resume.py 已实现）

| 规则 | 行为 |
|---|---|
| 教育段位置 | `campus` 置顶；`experienced` / `expert` 沉底 |
| 校园内容 | 标 `student_era: true` 的条目在社招 / 资深画像下自动过滤 |
| 技能收敛 | 社招：过滤 `archived` → 过滤无佐证且非 `keep` → 超 10 项告警 |
| `expert` 画像 | 不渲染技能清单段（能力应写进经历） |
| 求职意向 | 默认不渲染，`show_intention: true` 才输出 |
| 页脚标注 | 校对模式显示当前画像与包装级别，避免"不知道自己用了什么档" |

技能段的处理：`evidence_refs` 为空的技能只有本人陈述、没有项目能佐证，排序靠后，校对模式标「○无项目佐证」。这不是说它假，而是提醒——**面试官看到"熟悉 X"却找不到相关项目时会质疑**。

**"半生效"比"不生效"更危险**——只降级句首动词、句中还留着"主导"，看起来改过了其实没有。故渲染器会对整句复查，残留的强主张词一律告警。
